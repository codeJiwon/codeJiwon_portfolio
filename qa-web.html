발견

직접 만든 테스트 데이터로는 검증을 통과했으나, 팀이 보유한 실제 회의록 5건으로 재검증하자 전혀 다른 결함이 드러났습니다. 원문에 연도가 한 번도 언급되지 않았는데 AI가 마감일을 2023-08-22로 지어내고 있었습니다. 자체 제작 데이터는 전부 상대 표현이라 이 유형의 오류가 발생할 수 없는 데이터였습니다.

조치

프롬프트를 정교하게 다듬는 대신 서버에서 결과를 방어하는 3중 구조를 구현했습니다. ① AI가 제시한 근거 ID를 실제 입력에 존재하는 것만 통과시키는 화이트리스트 검증 ② 계층(H1·H2·H3)을 잘못 반환해도 서버가 트리 깊이 기준으로 재계산하는 정규화 ③ 날짜 계산을 모델 추론에서 분리해 서버의 결정적 로직으로 이관. 판단 불가능한 값은 추측 대신 사용자 확인이 필요한 상태로 표시하도록 설계했습니다.

# AI가 근거로 제시한 ID 중 실제 입력에 존재하는 것만 통과시킨다 evidence_ids = [ s for s in (topic.get("evidence_segment_ids") or []) if s in valid_ids ] # H3(depth 3) 아래로는 계층 생성 자체를 차단한다 children = [] if depth >= 3 else normalize_topic_tree( topic.get("children", []), depth + 1, valid_ids )

존재하지 않는 근거가 결과에 섞이는 경로와, 4단계 이상 깊어진 계층이 그대로 통과하는 경로를 각각 차단

원인분리

경량 모델의 규칙 위반은 상위 모델 교체 후 사라졌으나 마감일 오류는 두 모델 모두에서 동일하게 재현됐습니다. 이를 모델 성능이 아닌 서버 로직의 결함으로 판단했고, 이후 두 모델에서 모두 재현되면 코드 결함, 한쪽에서만 재현되면 모델 한계로 구분하는 기준을 세웠습니다.

결과

확인한 결함을 매번 회귀 테스트로 고정해 3개에서 12개까지 확대했습니다. 검증이 자산으로 쌓이면서 모델을 통째로 교체하는 변경도 결과 비교만으로 판단할 수 있게 됐고, 반복 확인에 드는 시간이 사라졌습니다. 검증 범위를 백엔드에 한정하지 않고, 생성된 계층을 렌더링하는 프론트엔드(JS) 데모의 트리 파싱 버그까지 찾아 수정했습니다.

재현 조건이 특수한 동시성 결함 추적 — "가끔 로그아웃되는" 증상

일루와 (with1LU) · 2026.03 – 08

Swift 6 · async/await · Actor · Clean Architecture

증상

특정 상황에서만 사용자가 로그아웃되는 문제가 재현 조건 없이 산발적으로 보고됐습니다.

원인

홈 진입 시 프로필·경기 정보 API가 동시에 401을 받으면 토큰 갱신이 두 번 호출되고, 두 번째 갱신은 이미 무효화된 refresh token으로 요청되어 실패 → 세션 종료로 이어지고 있었습니다. 요청이 순차적으로 실행되는 화면에서는 재현되지 않아 발견이 늦어진 결함이었습니다.

조치

Swift actor 격리를 이용한 single-flight 패턴으로, 진행 중인 갱신이 있으면 새로 시작하지 않고 결과를 공유하도록 설계했습니다. 동시 N개 요청에도 갱신 API 호출이 정확히 1회임을 보장합니다. 갱신 요청 자체가 401을 받아 무한 루프에 빠지는 경로는 requiresAuthentication 플래그로 재시도 대상에서 제외해 구조적으로 차단했습니다.

actor TokenRefreshCoordinator { private var refreshTask: Task<Void, Error>? func refresh(_ operation: @escaping () async throws -> Void) async throws { if let refreshTask { try await refreshTask.value // 진행 중이면 결과를 공유 return } let task = Task { try await operation() } refreshTask = task defer { refreshTask = nil } // 성공·실패 모두 정리 try await task.value } }

actor 격리로 상태 접근이 직렬화되어, 갱신이 중복 실행되는 경로 자체가 사라짐

재발

수정 후에도 일부 화면에서 동일 증상이 재발했습니다. 추적 결과 여러 Repository가 기본값으로 DefaultAPIClient()를 각자 생성해, 갱신 로직이 주입된 공유 인스턴스가 아닌 빈 인스턴스를 사용하고 있었습니다. 9개 Repository의 의존성을 공유 인스턴스로 통일한 뒤, 코드 전체 검색으로 직접 생성이 0건임을 확인하고 재발 방지 규칙으로 문서화했습니다.

남은 과제로 기록한 것 — Actor 격리는 런타임에서 구조적으로 보장되지만, 동시 요청에 대한 자동화 통합 테스트는 아직 작성하지 못했습니다. 현재는 프록시 툴로 두 요청을 동시에 401로 응답시키는 수동 테스트로 검증하고 있으며, 자동화가 다음 단계입니다.
