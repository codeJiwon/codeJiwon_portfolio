역할: iOS 프론트엔드 단독 개발 · 기간: 2026.03 – 2026.08 · 백엔드 팀과 GitHub Flow PR 협업

인증 흐름 진단 — 갱신 코드는 있는데 로그인이 풀리는 문제

RefreshToken 발급 API의 DTO·Endpoint·Repository·UseCase가 이미 전부 구현되어 있었는데도, 일부 화면에서 401을 받으면 곧장 "로그인 정보가 만료되었습니다"가 떴습니다. 추적해보니 RefreshTokenUseCase는 DIContainer에 "등록"만 되어 있을 뿐 어떤 ViewModel에도 실제로 주입되지 않은 죽은 코드였고, APIClient는 401을 받으면 갱신을 시도하지 않고 그대로 NetworkError.unauthorized를 던지기만 했습니다. 부품은 다 있었지만 그 부품들을 잇는 흐름이 빠져 있었던 것입니다.

동시 401 요청의 토큰 중복 갱신 제거

홈 진입 시 프로필·경기 정보 API가 동시에 401을 받으면 토큰 갱신이 두 번 호출되고, 두 번째 갱신은 이미 무효화된 refresh token으로 요청되어 로그아웃되는 문제를 발견했습니다. Swift actor의 격리 모델을 활용한 single-flight 패턴으로, 진행 중인 갱신 Task가 있으면 그 결과를 공유하도록 설계해 동시 N개 요청에도 refresh API가 정확히 1회만 호출되도록 보장했습니다.

actor TokenRefreshCoordinator {
    private var refreshTask: Task<Void, Error>?

    func refresh(_ operation: @escaping () async throws -> Void) async throws {
        if let refreshTask {
            try await refreshTask.value   // 이미 진행 중이면 결과 공유
            return
        }
        let task = Task { try await operation() }
        refreshTask = task
        defer { refreshTask = nil }       // 성공/실패 모두 정리
        try await task.value
    }
}

알려진 한계 — Actor 격리는 런타임 내에서 구조적으로 보장되지만, 동시 요청에 대한 자동화 통합 테스트는 아직 작성되지 않았습니다. 프록시 툴을 이용한 수동 테스트로 검증했습니다.

갱신 로직 자체가 무한 루프에 빠질 위험도 있었습니다 — refresh 요청(POST /auth/refresh-token)도 결국 네트워크 요청이라, 이 요청 자체가 401을 받으면 다시 refresh를 시도할 수 있기 때문입니다. Endpoint에 requiresAuthentication 플래그(기본값 true)를 추가해 로그인·토큰갱신 엔드포인트는 401 재시도 대상에서 제외시켜 구조적으로 차단했습니다. 또한 Core 계층인 APIClient가 실제 갱신을 수행하는 Data 계층의 AuthRepository를 직접 참조하면 의존성 방향이 역전되므로, Core에는 TokenRefreshing 프로토콜만 두고 Data가 AuthTokenRefresher로 구현한 뒤 DIContainer가 주입 지점에서 연결하도록 분리했습니다.

공유되지 않은 APIClient 인스턴스 — 재발한 로그아웃 버그

위 로직을 다 붙인 뒤에도 일부 화면에서는 여전히 즉시 로그아웃되는 문제가 재발했습니다. 원인은 여러 Repository가 초기화 파라미터 기본값으로 = DefaultAPIClient()를 각자 새로 생성하고 있었다는 것 — DIContainer가 tokenRefresher를 주입해둔 공유 인스턴스가 아니라, tokenRefresher가 nil인 별도 인스턴스를 쓰고 있었습니다. DIContainer의 apiClient를 공유 가능하도록 노출하고, Avatar·Home·Game·Stadium·Mate·User·GameLog·Team·Upload 등 9개 Repository의 기본값을 전부 DIContainer.shared.apiClient로 통일했습니다. 코드 전체를 검색해 DefaultAPIClient() 직접 생성이 0건임을 확인한 뒤, 새 Repository를 추가할 때 지켜야 할 규칙으로 문서화했습니다.

Keychain 전환 · 세션 만료 자동 복구

초기에는 UserDefaults에 토큰을 평문 저장했으나, 기기 백업 노출 가능성과 앱스토어 심사 기준을 고려해 외부 라이브러리 없이 Security 프레임워크를 직접 래핑해 Keychain으로 전환했습니다. kSecAttrAccessibleAfterFirstUnlock을 적용해 백그라운드 토큰 갱신을 지원하면서도 앱 삭제 시 항목이 자동 제거되도록 했고, sessionDidExpire 알림으로 네트워킹 레이어와 UI 레이어를 완전히 분리했습니다. 구독 측에서는 Combine 대신 for await _ in NotificationCenter.default.notifications(named:)로 알림을 소비해, 프로젝트 전반의 async/await 스타일과 일관성을 유지했습니다.

커스텀 APIClient — 팀 추가 비용을 낮추는 인프라

Moya 대신 URLSession 기반 커스텀 APIClient를 직접 구축했습니다. Endpoint 구조체 하나만 작성하면 인증 헤더 부착·401 갱신 재시도·에러 분류가 자동으로 처리되어, 11개 API 그룹이 동일한 패턴으로 추가됐고 인증 누락·재시도 빠짐 같은 반복 실수가 구조적으로 발생하지 않았습니다.

서버 불안정 상태코드를 도메인 enum으로 흡수

문서화 없이 LIVE / PROGRESS / ING / END / FINISH / FINAL 등이 혼재하는 gameStateCode를 contains 기반 우선순위 매핑으로 도메인 GameState enum에 흡수시켜, 뷰 레이어에는 문자열 분기 로직이 전혀 없도록 설계했습니다. (오분류 가능성이 있는 한계도 포트폴리오에 명시)

팀 로고·팀명 데이터 소스 불일치 — 같은 원칙의 재발견

온보딩 구단 선택과 마이페이지 구단 변경 화면에서 로고는 맞는데 구단명 텍스트만 다르게 표시되는 문제가 있었습니다 — 로고는 team.id → KBOTeam 매핑으로 계산하면서, 이름은 서버가 내려주는 team.name을 그대로 쓰고 있었기 때문입니다. 서버의 팀 이름 배열 순서가 클라이언트 로고 순서와 어긋나 있어, 한 화면 안에 두 개의 서로 다른 데이터 기준이 섞여 있었던 것입니다. 이름도 team.name 대신 KBOTeam.rawValue로 통일하고 두 화면이 같은 TeamLogoCell을 공유하도록 정리해, 위 gameStateCode 사례와 동일한 원칙 — 여러 데이터 소스를 하나의 domain entity 기준으로 통일한다 — 을 다시 적용했습니다.

아바타 레이어 합성 · S3 Presigned Upload

6개 슬롯(BODY/BOTTOM/TOP/HEAD/FACE/ACCESSORY)을 레이어 순서 타입으로 명시해 합성 버그를 컴파일 타임에 방지했고, 렌더 → 전신 업로드 → 얼굴 크롭 업로드 → 서버 반영의 순차 파이프라인을 구현했습니다. 부분 실패 시 S3 고아 객체가 남는 한계도 인지하고 문서화했습니다.

갤러리 업로드 썸네일 미표시 — S3 object key 판별

직관 로그에 갤러리 사진을 올려 저장해도 카드 목록의 썸네일이 표시되지 않았습니다. 서버 응답을 확인해보니 thumbnailUrl에는 실제 URL이 아니라 game-log-photo/a8c4e568-....jpg 같은 S3 object key가 내려오고 있었는데, 기존 ServerImageURLResolver는 절대 URL이 아닌 값이면 무조건 API base URL을 붙이도록 되어 있어 존재하지 않는 https://dev.with1lu.site/game-log-photo/... 주소로 변환하고 있었습니다. object key 패턴(game-log-photo/, avatar/, icon/)을 감지해 S3 bucket URL로, 그 외 값은 기존처럼 API base URL로 분기하는 로직을 추가했습니다.

enum ServerImageURLResolver {
    private static let s3BaseURL = URL(string: "https://with1lu-dev-bucket.s3.ap-northeast-2.amazonaws.com")!

    static func url(from value: String?) -> URL? {
        guard let trimmedValue = value?.trimmingCharacters(in: .whitespacesAndNewlines),
              !trimmedValue.isEmpty else { return nil }

        if let absoluteURL = URL(string: trimmedValue), absoluteURL.scheme != nil {
            return absoluteURL   // 이미 절대 URL이면 그대로 사용
        }

        let path = trimmedValue.hasPrefix("/") ? String(trimmedValue.dropFirst()) : trimmedValue

        if path.hasPrefix("game-log-photo/") || path.hasPrefix("avatar/") || path.hasPrefix("icon/") {
            return s3BaseURL.appendingPathComponent(path)   // S3 object key
        }
        return APIEnvironment.baseURL.appendingPathComponent(path)   // 그 외 상대 경로
    }
}

업로드 성공만으로는 기능이 완성되지 않는다는 것도 함께 확인했습니다 — 서버가 저장·반환하는 값이 절대 URL인지 object key인지에 따라 클라이언트의 URL 해석 규칙이 달라지므로, 이미지 URL 처리는 공통 resolver 하나로 모으고 S3 key와 API 상대 경로를 명확히 구분하는 것이 핵심이었습니다.

완성도 있는 엣지 케이스 처리

  • Apple 재가입 온보딩 분기 — 탈퇴 후 같은 Apple 계정으로 재가입할 때, 클라이언트의 로컬 차단 상태와 서버의 "신규 가입 가능" 상태가 충돌해 온보딩이 중간에 끊기던 문제를 서버 isNewUser/로컬 needsRegistration 기준으로 재정리
  • 갤러리 업로드 Content-Type 불일치 — HEIC로 읽힌 원본을 무조건 image/jpeg로 업로드해 디코딩에 실패하던 문제를 업로드 전 JPEG 데이터로 정규화해 해결

베이스라인 촬영 시 치아 픽셀의 L*a*b* 평균·표준편차로 개인별 ToothColorProfile을 생성하고, 검사 픽셀이 이 분포에서 얼마나 벗어나는지 축별 표준화 유클리드 거리로 측정합니다. 정식 Mahalanobis distance는 아니지만(공분산 행렬 미사용) 구현 단순성 대비 실용적 효과를 제공한다는 점을 명확히 표기했습니다.

8존 공간 분석 + 위치 인코딩 햅틱

전체 ΔE 점수만으로는 위치를 알 수 없어, 치아 영역을 4열×2행 = 8개 존으로 분할하고 좌/우 존 이상 시 방향별 진동 타이밍을, 상악 이상 시 sharpness를 강화(0.8 vs 0.4)해 화면 없이도 위치를 촉각으로 인지할 수 있도록 설계했습니다. 모든 결과는 음성 + 햅틱 + 시각 세 채널로 동시 전달됩니다.
